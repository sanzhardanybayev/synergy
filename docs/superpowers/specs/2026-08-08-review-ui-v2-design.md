# Synergy Review UI v2 - File-Centric Stage, Parallel Sessions, Theme Fixes

- **Status:** Approved (conversational design approved 2026-08-08)
- **Date:** 2026-08-08
- **Relationship to existing Synergy:** Iterates on the guided review feature designed in
  `2026-07-19-synergy-review-design.md`. That feature lives on the unmerged branch
  `codex/review-analysis-efficiency` (plugin version 0.13.0, identical to the installed
  plugin cache). This spec assumes that branch is landed on `main` first.

## Problem

The shipped review UI presents one review item (diff hunk or code section) at a time in a
three-column layout, with per-hunk rows duplicated in the sidebar. Three problems:

1. **Layout.** The reviewer wants a file-centric flow: files in the left sidebar, and for
   the selected file a broad file-level description plus the file's hunks as tabs, each
   hunk carrying its own description. Today there is no file-level description at all and
   the sidebar mixes file and hunk navigation.
2. **Light theme is unreadable.** The review surface was developed against the dark theme;
   several review-specific styles do not resolve to readable colors in light mode, forcing
   a theme switch to work. There are also polish defects, notably checkboxes overlapping
   row borders in the sidebar list.
3. **No session browser.** Review workspaces already persist independently under
   `.synergy/reviews/<workspace>/`, and the route
   `/review/:workspaceId/:revisionId` is already per-workspace, but there is no index UI.
   The intended workflow - N sub-agents each preparing a review session for a different
   PR, the human opening them later at leisure - has no landing surface.

## Goals

- Land the review branch on `main` and build on top of it.
- File-centric review stage: files in the sidebar, hunks as tabs within the stage,
  file-level broad description plus per-hunk descriptions.
- One concise repository-aware description per file, generated by the review skill and
  carried through reconciliation.
- A review index page listing all review workspaces with progress, so many concurrently
  prepared sessions can be discovered and opened.
- Light theme readability and polish fixes, verified in a real browser in both themes.

## Non-goals

- Any change to the question loop, agent presence, or readiness gate.
- Revision-history UI changes.
- The VS Code / Cursor extension (separate spec:
  `2026-08-08-vscode-extension-design.md`).
- Cloud persistence or cross-repository session aggregation.

## Design

### A0. Foundation: land the review branch

`codex/review-analysis-efficiency` contains the entire review feature
(`codex/synergy-review` and `codex/review-runtime-readiness` are its ancestors), `main`
is a pure ancestor of it with zero commits ahead, and its tree matches the installed
0.13.0 plugin cache. Landing it is a fast-forward merge.

Implementation notes:

- The working tree currently holds untracked copies of
  `docs/superpowers/plans/2026-07-19-synergy-review.md` and
  `docs/superpowers/specs/2026-07-19-synergy-review-design.md` that also exist on the
  branch. Compare and remove the untracked copies before merging so the merge does not
  abort.
- All subsequent work in this spec is a behavior change under `packages/` and `skills/`
  and must bump the plugin version per the release gate.

### A1. Stage relayout: files left, hunks as tabs

**Sidebar** (`ReviewSidebar`):

- Shows groups and files only. Per-hunk rows are removed from the sidebar.
- Each file row keeps its tri-state checkbox (all reviewed / partial / none) and gains a
  reviewed count, for example `2/3`.
- Selecting a file row activates the file in the stage. The active file is highlighted.
- The search filter continues to match file paths.

**Stage** (`ReviewStage` becomes file-scoped):

- Header: file path, change kind, and the file-level broad description (A2).
- Below the header, a **hunk tab strip**: one tab per review item in the file, labeled
  `Hunk N` (diff reviews) or the section label (scoped reviews), with the item's
  reviewed state visible on the tab (check mark).
- The active tab renders exactly what the current single-item stage renders: the
  immutable diff hunk or source section with selectable lines, then the item's
  description, private note, and Mark reviewed action.
- File-level changes with no textual rows (binary, renames) render as today via
  `FileChangeViewer`, as a single tab.

**Selection model:** the active review item remains the single source of truth
(`activeItemId`). The active file is derived from it. Selecting a file activates its
first unreviewed item, falling back to its first item.

**Keyboard:** `J`/`K` move across items in order and roll over across file boundaries
(the stage switches files automatically). `R` toggles reviewed. `?` focuses the question
input. Unchanged semantics, new presentation.

### A2. File-level insights (schema and skill)

- `skills/review/templates/analysis-schema.json` gains a `files` array:
  `[{ "path": string, "description": string, "confidence": "high"|"medium"|"low" }]`.
  One entry per changed file (diff reviews) or per scoped file (scope reviews).
- The review skill's analysis step generates the per-file broad description alongside
  the existing per-item descriptions, with the same conciseness rules.
- `@synergy/review-core` stores file insights in the insights document and exposes them
  in `ReviewBundle`.
- **Reconciliation:** when a new revision carries forward all of a file's items
  unchanged, the file description is carried forward too; if any item in the file is new
  or changed, the file description is regenerated with the items.
- **Backward compatibility:** bundles produced before this change simply have no file
  insights; the stage omits the file description block and renders normally.

### A3. Review index page

**Server:** `GET /api/reviews` on the preview daemon scans `.synergy/reviews/` and
returns, per workspace: workspace id, subject label (for example `PR #317 - <title>`,
`Staged changes`, `Scope: packages/cli`), latest revision id, item counts and reviewed
counts for that revision, open question count, and created/updated timestamps. Corrupt
or unreadable workspaces are reported as degraded entries, never thrown.

**Client:** the `/review` route (no params) renders the index: a card per workspace,
newest first, with subject, progress bar, updated time, and badges (`complete`,
`questions open`, `degraded`). Clicking a card navigates to
`/review/:workspaceId/:latestRevisionId`.

**Parallel creation:** sub-agents already create workspaces through the skill and CLI
into separate directories with atomic writes and locks; no changes needed for
concurrency. `active-review.json` remains a last-opened pointer used by the feedback
flow; the index page removes any reliance on it for discovery.

### A4. Theme and polish fixes

- Audit the review UI in the **light theme** with a real browser (chrome-devtools-axi):
  diff row backgrounds and text, descriptions, sidebar, tab strip, buttons, question
  rail.
- Root-cause expectation: `review.css` styles that do not resolve to readable values
  from the light `--syn-*` token set. Fixes are token-driven only; no hardcoded palette
  hex values, per the design-system rule. Missing semantic tokens are added to
  `theme.css` with values for both themes.
- Fix the checkbox/border overlap on sidebar rows (spacing and alignment, not visual
  hacks).
- While auditing, fix other clearly-off visuals in both themes in the review surface.
- Verification: before/after screenshots in both themes.

### A5. Testing

- Unit: file-insight schema validation, reconciliation carry-forward of file
  descriptions, `/api/reviews` scanner (empty directory, corrupt workspace, many
  workspaces).
- Component: hunk tab strip states, sidebar file rows (complete/partial/none), stage
  fallback when file insights are absent.
- Manual browser pass: light and dark themes, keyboard flow across file boundaries,
  index page with ten workspaces.

## Error handling

- Index scanner degrades per-workspace, never fails the whole listing.
- Missing file insights render nothing rather than a placeholder error.
- Reconciliation failures fall back to regenerating descriptions, matching existing
  item-level behavior.
