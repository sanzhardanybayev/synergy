# Plugin Freshness Guard — Design

**Date:** 2026-06-26
**Status:** Approved design, pending implementation plan
**Author:** Synergy maintainers (with Claude)

## Problem

A real user (the maintainer, dogfooding in `phactor-workspace`) generated a spec
session whose `02-implementation.mdx` used the **pre-`AgentTree`** authoring
shape — old `<AgentAllocation>` with `type`/`responsibility` and numeric phases,
legacy `<Timeline milestones={…}>`, and **no `<AgentTree>` at all**. The
`<AgentTree>` agent-graph + per-node model/effort feature was entirely absent
from the generated output.

### Root cause

The session was generated by the **0.5.0 `create-spec` skill** even though the
0.6.0 skill (which contains the `AgentTree` authoring guidance) was already on
disk. Two distinct failures combined:

1. **Stale running session.** Claude Code resolves plugin skills at *session
   start*. The `phactor-workspace` session was already running on 0.5.0 when the
   plugin was upgraded to 0.6.0 on disk (~06-25 23:26); it kept authoring with
   the 0.5.0 templates when it generated the spec (~06-26 00:10). An in-flight
   on-disk upgrade does not hot-swap a live session.
2. **Shipped without a bump.** `AgentTree` landed under the *same* `0.6.0`
   version (0.6.0 had already been bumped for the live-timeline work), so
   `/plugin update` detection keys on a version that didn't move.

A third latent failure the maintainer wants covered:

3. **User never updates.** Even a correctly-published new version does nothing if
   the user never runs `/plugin update` and their cache stays old.

The generated file is a fingerprint match for the 0.5.0 template (import line,
`<Timeline milestones>`, `<AgentAllocation>` shape) — confirming the wrong skill
version produced it.

## Goals

Ensure users always run the latest plugin *behavior* after an update, by guarding
all three failure modes above. The guard is **fix-forward**: it protects from the
version that first ships it onward (it cannot retroactively fix 0.5.0).

When a running session is detected as stale, the chosen behavior is **warn
loudly, then proceed** — not hard-block, not auto-heal. (Decision by the
maintainer; favors simplicity and avoids false-positive disruption.)

## Non-goals

- Hot-reloading skills into a running session (not possible; restart is the
  remedy).
- Blocking generation on staleness (explicitly rejected — warn-and-proceed).
- A general plugin auto-updater (we lean on Claude Code's native `/plugin`
  update flow for delivery).

## Architecture

Three coordinated layers. They are coupled by **one stamped version marker**: the
author-side release gate maintains it; the runtime guards read it.

```
plugin.json.version  ──(version-sync)──>  marketplace.json version
        │                                  every skills/*/SKILL.md  "synergy-version:" stamp
        │
        ├── author-side (this repo):   lefthook auto-stamp  +  CI bump/consistency gate
        └── runtime (ships in plugin): SessionStart hook  +  skill Step-0 preflight
```

### The backbone: one version, stamped everywhere

- **Source of truth:** `plugin.json` → `version`. Nothing else is hand-edited.
- **Derived, never hand-written:**
  - `.claude-plugin/marketplace.json` plugin `version`
  - a `synergy-version: X.Y.Z` stamp in every `skills/*/SKILL.md`
- **Detection primitive (shared, pure-local, no network):**
  `newest_installed = ls ~/.claude/plugins/cache/synergy/synergy/ | sort -V | tail -1`
- **Staleness comparison (shared):** stale iff `mine != newest_installed` AND
  `mine` sorts before `newest_installed` under `sort -V`. (Guards against a
  downgrade reading as "stale".)
- **How each caller knows `mine`:**
  - **hook:** parses it from `$CLAUDE_PLUGIN_ROOT` (path ends `…/synergy/<version>/`).
  - **skill:** reads the stamped literal from its own `SKILL.md` text — the only
    reliable signal a *skill* (whose text is what's stale) has about its own
    version. This is why the stamp is the linchpin.

## Components

### 1. `scripts/version-sync` (author-side stamper)

Reads `plugin.json.version` and writes it into `marketplace.json` and the
`synergy-version:` stamp of every `skills/*/SKILL.md`. Idempotent (no-op when
already in sync). Exit non-zero only on I/O error.

### 2. lefthook pre-commit — auto-stamp, never block

Add a `version-sync` command mirroring the existing `biome` command's
`stage_fixed: true` pattern: run the stamper, re-stage any files it touched.
Consequence: marketplace.json and all SKILL.md stamps are *always* in lockstep
with `plugin.json` on every commit, with zero friction. Drift becomes
structurally impossible.

```yaml
pre-commit:
  parallel: true
  commands:
    biome: { … existing … }
    version-sync:
      glob: ".claude-plugin/plugin.json"
      run: node scripts/version-sync.mjs
      stage_fixed: true
```

(Also runs when SKILL.md/marketplace.json are staged, to re-assert the stamp.)

### 3. CI gate on the default branch — authoritative "no ship without a bump"

A GitHub Action on PRs and pushes to `main` that fails when either:

- **consistency** — `marketplace.json` or any `SKILL.md` stamp ≠
  `plugin.json.version` (catches a hand-edit that bypassed the stamper); or
- **bump** — any file under `skills/`, `packages/`, `commands/`, or `hooks/`
  changed in this PR, but `plugin.json.version` is unchanged between the PR base
  and head.

**Comparison basis:** the repo currently has **no git tags** (0 tags); version
history lives in `plugin.json` commits. So the gate diffs `plugin.json.version`
across the change rather than against a tag: on a PR, `origin/main` (base) vs
`HEAD`; on a push to `main`, the push's before-SHA vs after-SHA. Tagging releases
is recommended going forward but the gate does not depend on it.

**Behavior dirs:** `skills/ packages/ commands/ hooks/`. **Explicitly excluded as
non-behavioral:** `examples/`, `docs/`. CI is chosen over a local pre-push gate
because pushing a feature branch is not releasing — the real release boundary for
a GitHub marketplace is "it landed on the branch users pull from."

This is the layer that would have caught `AgentTree` shipping under 0.6.0.

### 4. SessionStart hook (ships in the plugin)

`hooks/hooks.json` registers a `SessionStart` command calling
`${CLAUDE_PLUGIN_ROOT}/hooks/freshness.sh`:

- Parse `mine` from `$CLAUDE_PLUGIN_ROOT`; compute `newest_installed` locally.
- If stale, print a notice (SessionStart stdout is injected as agent context):
  > ⚠ synergy: this session loaded vMINE, but vNEWEST is installed. Restart
  > Claude Code to load the latest skills/templates.
- **Upstream check (best-effort):** `git ls-remote --tags <repo>` with a **3s
  timeout, silent-fail**; only *adds* a "vNEWEST published — run `/plugin update`"
  line when it succeeds and finds a newer tag. The offline/local path stays
  instant; the network is pure upside. (Throttling to once/day is a future option
  if it proves noisy; not in v1.)

### 5. Skill Step-0 preflight (ships in the plugin)

Prepend a short "Step 0: freshness check" to `create-spec`, `execute`,
`spec-authoring`, and `resume`. It is **self-contained inline bash** (no
dependency on locating a shipped script, since a stale skill may not know its
plugin root):

- The model reads its stamped `synergy-version` from its own text.
- It runs the one-liner to get `newest_installed` and applies the shared compare.
- If behind, it surfaces the loud warning to the user, **then proceeds**.

This is the **point-of-use catch** — it fires exactly when `create-spec` would
otherwise scaffold with stale templates (the phactor incident).

## Data flow

1. Maintainer bumps `plugin.json.version` for a behavior change.
2. `version-sync` (pre-commit) propagates it to marketplace.json + SKILL.md stamps.
3. CI on `main` refuses the change if behavior dirs moved without a bump, or if
   stamps are inconsistent.
4. User runs `/plugin update`; the new version lands in the cache.
5. **SessionStart hook** on the user's next session compares resolved vs newest
   installed and warns if behind; best-effort upstream line nudges `/plugin update`.
6. **Skill preflight** compares the running skill's stamp vs newest installed at
   the moment of use and warns before scaffolding if behind.

## Error handling

- All runtime checks **fail open**: any error (missing cache dir, parse failure,
  network timeout) produces *no* warning rather than blocking or erroring. A
  freshness guard must never break a session.
- `sort -V` handles multi-digit semver (`0.9.0` < `0.10.0`).
- Downgrades (`mine > newest_installed`) are treated as *not stale*.
- The hook's notice is agent-mediated (injected context), so the agent is
  responsible for surfacing it; phrased imperatively so it is passed through.

## Limitations (stated, not hidden)

- **Fix-forward:** only protects from the introducing version (0.7.0) onward.
- **Warn-only:** relies on the user to restart / update (by design).
- **"Newest installed" ≠ "newest published"** except via the best-effort network
  line.
- Multiple cache dirs may include a broken/partial install; `max()` could point
  at a dud. Acceptable for a warn-only guard.

## Testing

- **`version-sync`:** unit — a bump propagates to marketplace.json + every stamp;
  idempotent re-run is a no-op.
- **CI bump-gate logic:** table — behavior-dir change without bump → fail; bump
  present → pass; docs/examples-only change → pass; stamp mismatch → fail.
- **`sort -V` compare:** table — equal (fresh), `mine<newest` (stale),
  `mine>newest` (fresh/downgrade), `0.9.0` vs `0.10.0` (stale).
- **SessionStart hook:** integration — fixture `CLAUDE_PLUGIN_ROOT` + fake cache
  tree; assert the warning appears only when stale and never on error.
- **Skill preflight:** test the underlying one-liner against fixture cache trees
  (the prose step wraps it).

All under the existing `pnpm -r test` (vitest) setup; shell scripts wrapped so
vitest can invoke them.

## Rollout

Ships as **0.6.0 → 0.7.0** — the first version the new bump-gate itself would
require. Because the guard is fix-forward, 0.7.0 is the baseline from which all
future staleness is caught; the already-generated phactor session is fixed
separately (out of scope here).
